# 07 — Design Spec schema v1

**What to build:** The Pydantic model set that defines `design.yaml` — the
artifact that replaces ten generated Python scripts as the thing that *is* the
simulation. v1 covers all five canonical cases — inset-fed patch, bowtie, microstrip
line, coupled-line filter, **and the horn** (Q1: full geometry including
sweeps and lofts, built on the HFSS native modeler rather than an external
CAD kernel). Sections mirror the Spine so the
mapping stays obvious: `solution_type`, `variables`, `geometry`, `materials`,
`excitations`, `boundaries`, `mesh`, `setup` (+ sweep), `qa_signals`, plus a
`provenance` block naming the recipe source and, for paper-sourced designs, the
canonical reading per key dimension (this is where ticket 09 of the perf refactor
lands as data instead of prose). Three decisions carry most of the value.
**Symbolic selectors:** faces and objects are referenced as
`face_of(PatchBowtie, +z)` / `nearest_face(Substrate, [x,y,z])`, never ids or
edges — encoding env-compat #7/#8 as a type rather than a remembered rule.
**Mandatory units** on every dimensional value (`52.64mm`, `3.5GHz`), so unit
mismatch is a validation error rather than a silent geometry bug. **Variables
first:** every geometry dimension is a variable reference or a literal-with-unit,
and the compiler emits AEDT design variables for all of them, making PLAN.md's
full-parameterization rule mechanical. Export JSON Schema from the same models
for the LLM's constrained decoding, so the validation contract and the generation
contract cannot drift.

**Blocked by:** 05 (the cases scope the schema honestly), 12a (its field-by-field
report is this ticket's input — Q7).

**Status:** ready-for-human

## Comments

- 2026-08-14: **Scope settled by the Q1-Q8 answers** in `phase-2-detail.md`.
- **Geometry ops (Q1 = c, native modeler).** The op list is: `box`, `sheet`,
  `cylinder`, `polyline`, `thicken_sheet`, `unite`, `subtract`, `intersect`,
  `sweep_along_vector` (carrying `draft_angle` / `draft_type`), `connect`
  (HFSS's loft/blend), `sweep_along_path`, `sweep_around_axis`, plus
  `import_cad` and `escape_hatch` for geometry that is received rather than
  designed. Every one of these already exists on `Modeler3D` and is already
  in the KB, so (c) costs ops in a schema, not a CAD kernel — and it keeps
  full parametrics, which an external kernel would destroy (imported CAD
  carries no construction history and cannot be parameterized).
- **Variables (Q2).** Expressions are first-class and are written through to
  AEDT as design-variable expressions, so the parametric link is live in the
  UI. The validator evaluates them only for dimensionality and cycles.
- **Selectors (Q3).** An ambiguous selector is an ERROR by default. Explicit
  `pick: largest_area | nearest: [x,y,z]` is the opt-in. Silent selection of
  the wrong face produces a model that builds fine and simulates nonsense,
  which is the worst failure class this tool has.
- **Mesh (Q4).** `adaptive_only` in v1; explicit mesh operations go through
  the escape hatch until there is a case that needs them.
- **Setup and sweep (Q6).** In the schema. Solve submission stays imperative
  under the watchdog (ADR 0006), unchanged.
- **Sequencing (Q7).** Ticket 12a (`snapshot_to_spec`) lands FIRST and its
  field-by-field report is this ticket's input, so the non-geometry ~70% of
  the schema is shaped by a real captured model instead of by guesswork. The
  geometry op list above is designed from the construction side, since a
  snapshot cannot distinguish a box from a lofted horn.
- **One spec per design (Q8).** The workspace holds one by default; Re-entry
  derives its spec via 12a from the copied project.

- 2026-08-15: **IMPLEMENTED** - `hfss_spec/schema.py`, with `hfss_spec/units.py`
  and `hfss_spec/expressions.py` underneath it. 61 Tier 0 tests.
  - **Op list complete** per the Comments above: all 14 construction ops plus
    `escape_hatch`, plus `unknown` for the reducer's honest placeholder.
  - **Selectors are types.** `FaceOf` / `ObjectRef` / `OuterFaces`, and a test
    asserts the exported JSON Schema contains no `face_id` / `edge_id` field
    anywhere. Ambiguity tie-breaks (`pick`, `nearest`) are mutually exclusive
    by validator.
  - **Units carry a dimensional algebra**, not just a suffix check: exponent
    vectors over length / time / resistance / angle, so `c0/f0` comes out a
    length and adding a frequency to a length is an error with a readable
    message.
  - **Unit literals inside expressions are handled.** AEDT writes
    `patch_L + 2mm` routinely and that is not valid Python; the evaluator
    lifts such literals to placeholders before parsing. Found by testing
    against real variable tables, not by design.
  - **Three findings from 12a are visible as fields** a from-scratch design
    would have missed: `project_variables` for the `$`-scope, inline
    `MaterialDef` alongside `MaterialRef` (the coplanar model's `myfr4` is not
    a library entry), and metal-as-`perfect_e`-boundary alongside
    metal-as-material.
  - **A schema decision worth recording: YAML 1.1 reads a bare `on:` key as
    boolean True.** The selector field is spelled `on:` throughout the design,
    so an unquoted spec failed with "Keys should be strings, got True", which
    tells an author nothing. The loader maps the boolean keys back; no spec
    field is spelled True, so it is unambiguous.
  - `knowledge/cases/patch-2400/design.yaml` (the model the 2026-08-15 run
    actually built and solved) and `knowledge/cases/bowtie-3500/design.yaml`
    (generated by 12a, then hand-completed from the pilot's own
    `src/02_geometry.py`, `src/03_materials.py` and `src/06_setup_sweep.py`)
    both validate clean.
