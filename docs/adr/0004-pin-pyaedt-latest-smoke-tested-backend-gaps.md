# Pin pyAEDT to the latest line; absorb backend-compat gaps via smoke tests

The plan assumed a pyAEDT release line "corresponding to" AEDT 2024 R1 had to be found and pinned. That premise dissolved on inspection: one pyAEDT release supports many AEDT versions (1.3.0 officially supports AEDT 2022 R1 and later, so 2024 R1 is in range), and the `/version/stable/` docs the KB was scraped from document exactly the latest pyAEDT line. Decision: pin the latest pyAEDT (1.3.0), keep the stable-docs KB, and handle the residual risk — APIs added after 2024 R1 (e.g. `get_rcs_data`, `MonostaticRCSExporter`) failing against the older backend — with a one-time smoke-test matrix whose outcomes are recorded in the playbook's environment-compat entry. Considered options: downgrading to a 2024-era pyAEDT (~0.9/0.10) with contemporaneous docs was rejected — it buys contemporaneity at the cost of permanently stale, buggier client code and the old `pyaedt.*` namespace; upgrading AEDT was rejected as a license/IT decision outside the project. Consequence: the KB is correct for the client library by construction, and backend-compat facts accumulate in exactly one place.
