# Solves run under a deterministic detached watchdog

The solve stage used to mean the agent launching `analyze(blocking=False)` and then polling — but in practice that became long foreground poll loops that silently hit the agent harness's 120-second bash timeout, then a sequence of process-detach hacks (Start-Process, WMI), four re-submissions, and one double-solve that cost an hour (observed 2026-08-02/03, 1.35 M-token run). Decision: the solve is orchestrated by two deterministic scripts — `08_solve.py` cleans stale results, probes for a solve already in flight (results-dir age + live solver processes; asks the user before submitting if one looks live), submits, and launches a detached `poll_solve.py` that writes `results/state/solve_progress.txt` from recursive `.asol`/`.sd` growth every ~20 s and exits on completion — or signals a stall when growth stops before convergence — and the agent does nothing but read that state file. No foreground polling by the language model, no solve-time estimation, no LLM babysitting. Considered options: a background cheap-model subagent watching the solve was rejected (tokens per poll for zero gain over a stateless script), and lengthening the bash timeout was rejected as the sole fix (it fixes the cap, not the attention cost of polling from a fat context). Consequences: solve watching costs ~0 LLM tokens and one read; the pre-submit guard hardens against the double-solve incident class; the `.aedtresults` recursive-glob + `cleanup_solution` patterns are codified instead of reinvented.
