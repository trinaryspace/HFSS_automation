§ 01The shape of a run

One conversation, one Workspace, three sessions, and exactly two places where a human has authority the tool will not take from them.

The workflow is packaged as an agent skill — hfss-agent — plus a repo of deterministic Python behind it. The skill supplies the doctrine; the Python supplies everything that can be checked without a language model. A run produces a Workspace at workspaces/<name>/ holding the staged scripts or the design document, the .aedt project file, machine state, the requested plots, and a summary.md carrying the design decisions and a cost run card.

Three kinds of request are in scope: a greenfield build (an antenna, filter, or RF part described in words), a Re-entry into an existing AEDT project — including one a human built — to change and re-solve it, and a solve/plots/results pass over a model that already exists. Re-entry never opens the original project: it is copied into the Workspace as a plain file operation and all work happens on the copy (ADR 0001).

The two human gates

Everything else in the design exists to make these two survive. First, the Clarification agreement: nothing is built until the user has confirmed the recipe, every stated assumption, and the QA signals that will judge the result. Second, the visual Review gate: the user inspects the built model in the AEDT window — never by reading the generated scripts — and nothing solves until they pass it (ADR 0003). Both caught defects in the pilots that no automated check saw, which is why they were kept when almost everything around them was rewritten.

§ 02Three phase sessions, bound by a ledger

A conversation used to be one 152-step session re-reading ~260 k tokens per step. It is now three short sessions that hand off through a small file.

  1. Clarification — <name>-clarify. One block: gather the minimum information, name the setup features the user left out, map the request onto a playbook recipe, state every assumption, propose the QA signals, lock the parameters and design variables. For a recipe taken from an academic paper it also cross-checks the paper's equations against its own table and figure readings and prints a dims cross-check verdict — an internally inconsistent paper is not a buildable recipe. the user confirmed the recipe, the assumptions and the QA signals, and state.md is written
  2. Build — <name>-build. Walk the Spine on the live desktop by one of the two routes, each stage closing with its verification line and a one-line ledger delta. Ends at the Review gate and read-back sync. validation passes, the user passed the gate, sync printed PASS, the ledger holds the snapshot pointer
  3. Solve + QA — <name>-solve. Submit under the detached watchdog, read only machine state while it runs, make the recipe's plots, run Result QA, bank the evidence, deliver the summary and run card. the plots exist in results/, every agreed signal is reported, the run card is appended

Each session starts fresh from workspaces/<name>/state.md — the State ledger — rather than from the prior conversation (ADR 0007). The ledger records stage progress, locked variables, decisions and pitfalls; machine state lives separately in results/state/*.txt and is never hand-edited. The ledger is the only resume point, so a killed session picks up from it instead of redoing clarification or re-writing scripts.

The phase is declared as the session's first action, and declaring it is what turns the boundary on:

python scripts/session.py --workspace workspaces/<name> --phase clarify → a clarify session cannot launch a desktop; only a solve session may solve

Once declared, the repo's own entry points refuse out-of-phase work with a non-zero exit rather than a warning, and the session carries a call budget (default 60) whose breach is an escalation verdict. This exists because prose did not bind: a measured session read the documented capability gap, quoted it correctly, and then spent 51 minutes and 151,526 tokens writing a field solver inside a Clarification block anyway.

§ 03The Spine

The solution-type-agnostic sequence every build walks. Under the compiler it is walked for you; under staged scripts it is one file per stage. The stages and their completion criteria are identical either way.

  1. Solution type — set explicitly from the recipe, never left at the default (the default is Terminal, not Modal).the design reports the recipe's type
  2. Design — created in the Workspace project and saved, clearing a stray lock if one exists.the project file exists on disk with the named design
  3. Geometry — every dimension a design variable, units per recipe, delete-then-create per solid.the solids match the recipe in the UI and each dimension is a variable, not a literal
  4. Materials — per recipe, tunables as variables, inline definitions where the library has no entry.each solid reports its recipe material
  5. Excitations & boundaries — port strategy per recipe, assigned by face object and never by id or edge.the ports and boundaries list matches the recipe
  6. Mesh — recipe mesh operations, or adaptive-only for proof stages.the mesh operations list matches the recipe, or is deliberately empty
  7. Setup + sweep — adaptive passes, delta-S, frequency, sweep range and interpolation.existing_analysis_sweeps shows the named setup with its sweep
  8. Validation — validate_simple() must pass; an invalid design is a failed stage.validation returns True
  9. Review gate — the built model presented in the AEDT UI, the user's tweaks read back, and the sync verified mechanically.the user passed the gate and sync verify printed PASS

Then the solve session: submit under the watchdog, post-process, Result QA, bank, summary. A stage is done only when its criterion is met and the user has seen that stage's state in the open desktop.

§ 04Two build routes

The Spine does not change between them. What changes is who writes the code that walks it — and that turned out to be the difference between a checkable build and an unbounded one.

Route A — Design Spec preferred

workspaces/<name>/design.yaml → hfss_spec/compiler.py

One typed YAML document describes the model; a hand-written, deterministic compiler builds it. No language model in that layer, ever. It is idempotent by construction, resolves symbolic face selectors itself, emits the same PASS: verification lines, and has absorbed the pyAEDT defects earlier runs paid for.

Measured on this box: it rebuilt the pilot's bow-tie with zero snapshot differences and zero bounding-box differences, and built the microstrip and the 10 GHz horn clean on the first attempt with no escape-hatch ops.

Route B — staged scripts fallback

workspaces/<name>/src/NN_<stage>.py

One stage, one script, one run. Used when the structure defeats the schema — and the ledger must say so, because the per-stage escape-hatch rate is a tracked metric rather than a quiet convenience.

Everything the free-form route needs to be safe still ships with it: the attach-or-launch preamble, the static gate, delete-then-create idempotency, and the replay-based sync verifier.

The whole argument for Route A is where errors get caught. Under Route B a malformed dimension costs a desktop launch, a failed stage, a traceback read and a self-correction round; under Route A it is a validator finding in about a second with no licence involved.

§ 05The Design Spec stack

Eight modules in hfss_spec/, all of them importable with no AEDT, no licence and no pyAEDT — which is what makes the build path checkable in milliseconds.

Schema v1 — three decisions encoded as types

The schema is Pydantic, and the rules that matter are structural rather than remembered. No field anywhere accepts a face or edge id — a port sits on {face_of: Feed, direction: "-y"}, resolved against the live model at build time, and an ambiguous selector is an error unless the spec opts in with pick: largest_area or a nearest: point. Units are mandatory: every dimensional value is a literal with a unit (52.64mm, 2.4GHz, 50ohm) or an expression over declared variables, and a bare number is legal only where the quantity is genuinely dimensionless. Variables come first: expressions pass through to AEDT verbatim, so a compiled microstrip reads back sub_W: 'trace_W + 12*h' in the variable table, not an evaluated number.

Geometry is expressed with fourteen authorable ops on the native HFSS modeler, plus one marker the snapshot reducer emits:

The offline gates

Validator

hfss_spec/validate.py · scripts/validate_spec.py

Four check classes past schema conformance: reference resolution (every selector names a declared object, every variable resolves, every material exists), units and dimensions (a frequency is never added to a length, extents are positive, the sweep brackets the target), topological sanity (a boolean's tools exist at the point it runs), and recipe completeness. Every finding carries its path — geometry[3].size[2] — so a diagnosis gets a location instead of a stack trace.

Physics pre-check

hfss_spec/physics.py · scripts/precheck.py

Closed-form estimators — rectangular and circular patch resonance, bow-tie resonance, microstrip impedance, pyramidal horn gain and optimum synthesis, waveguide cutoff, guide wavelength — predict the design's target and print the signed disagreement against it. Tolerances are data, in knowledge/playbook/precheck-tolerances.json, one per recipe.

It never blocks and never overrides: an INCONSISTENT verdict goes to the user with both numbers to arbitrate, and the choice is recorded in the spec's provenance.

Relational checks

hfss_spec/model_checks.py

Properties of the model as a whole, not of one field — added after a review found that all three real defects in six machine-clean specs were relational. A radiation boundary must clear what it bounds by λ₀/3; a lumped port sheet must be within 1.5× the width of the conductor it bridges. Both encode a geometric relation the author cannot satisfy by tuning a number they already control.

Snapshot reducer

hfss_spec/snapshot_to_spec.py · scripts/spec_from_snapshot.py

Turns a captured model_snapshot.json back into a design.yaml, so Re-entry gets a spec by reduction rather than archaeology. Exact for variables, materials, boundaries, ports, setup, sweep and solution type; explicitly approximate for geometry, where a bounding box is a consequence of a construction op rather than a restatement of it.

A worked verdict, from the pilot's bow-tie — the disagreement that survived four solves and roughly twenty hours the old way, surfaced here in microseconds:

target 3.5000 GHz closed-form 3.8782 GHz delta: +10.81% tolerance: 8% FAIL: precheck recipe=bow-tie-patch verdict=INCONSISTENT — arbitrate before building the built model measured 3.85 GHz — the estimator was right to +0.7%

Compiler and acceptance

compile_spec.py runs --dry-run (the full plan, no desktop) then --launch, refusing outright any spec that has not passed validation. Each stage still emits its PASS: line, so the ledger and self-correction contracts are untouched. hfss_spec/acceptance.py then answers the question that matters: does the compiled model match the snapshot the old path produced? It reuses the pilot's hard-won suffix-normalisation rule rather than a second copy of it, and classifies every residual difference as a compiler bug, a schema gap, or a capture gap — because "the diff is not empty" is not a finding.

§ 06Runtime contracts

The properties that hold on a live desktop regardless of route — each one written against an incident that cost real hours.

The verification line

Every stage ends with a single machine-parseable line carrying its assertions, and the self-correction loop reads that line rather than filtered logs:

PASS: geometry objects=4 variables=11 all_parameterized=True PASS: sync replay matches snapshot FAIL: sync mismatch — boundaries, variables

The port-pinned desktop

The session's desktop records its port and process id to results/state/aedt_port.txt and aedt_process_id.txt on first launch. Every later attach and every teardown reconnects by that recorded port, and a teardown with no pinned port refuses to act. That is what makes it impossible for the tool to close or kill the user's own AEDT session — including the second desktop the sync verifier launches, which tears down only its own.

Idempotency by delete-then-create

Every stage deletes the objects, boundaries, excitations, mesh operations and sweeps it recreates before creating them, so re-running a stage in place always converges (ADR 0008). This replaced teardown → wipe → replay chains — three of them in one observed build — with a single in-place re-run, and demoted wipe-and-rebuild to an explicit escalation. Under Route A it is a property of the compiler rather than a discipline the model must remember.

Read-back sync, verified mechanically

The user's UI tweaks must land back in the record or the scripts stop being a re-runnable one (ADR 0005). capture_state.py snapshots the live model — objects and bounding boxes, materials, boundaries, excitations, setups and sweeps, variables, sorted and rounded — into model_snapshot.json. Then, by route:

  • Route B: 12_verify_sync.py copies the workspace, replays the amended scripts on a port-pinned second desktop, captures the same shape there and diffs it, printing one PASS/FAIL line. Roughly eight minutes a round.
  • Route A: the same question is a snapshot diff against the as-built capture via spec_acceptance.py — seconds, no second desktop. Representable differences fold back into design.yaml; anything the schema cannot express gets a loud ledger entry naming it, so the spec is knowingly stale rather than quietly wrong.

Self-correction, with a cap

After each run the agent reads the verification line plus the error surfaces that actually work on this backend (validate_simple(), on-disk logs — the COM message manager is broken over gRPC). Correction is capped at three consecutive failed runs per stage, and escalates early on the identical error twice or on an error that maps to no known cause, attaching the script, the error and the attempted fixes.

§ 07Solve, bank, read out

The solve costs about zero language-model tokens to watch, cannot be declared finished without evidence, and cannot be torn down before its results are safe.

The detached watchdog

08_solve cleans stale results, probes for a solve already in flight — results directory age plus live solver processes — and asks the user before submitting if one looks live. It submits analyze(blocking=False), whose True return means submission and not completion, launches poll_solve.py as a detached process, and exits.

The watchdog imports nothing from pyAEDT — filesystem and process observation only. Every ~20 s it appends one line naming its stage (initial meshing → adaptive meshing → frequency sweep → finalizing → done) plus the evidence for that stage, drawn from the stage-family artifacts and the newest profile's stage ledger. It exits:

Watchdog terminal states
ExitStateEvidence required
0completethe profile's Status: Normal Completion, plus settle
2stalledno growth in the current stage past its window — the stage is named
3abortedany non-normal profile status, quoted verbatim; or in-flight markers gone with a dead solver

Terminal states are evidenced, never inferred from a plateau — an earlier settle-only rule declared an engine error complete. No output-count prediction is passed anywhere; the sweep-point guess class is gone. While it runs the agent tails the progress file and does nothing else: no foreground polling, no solve-time estimates.

Banking

A solve is not finished until confirm_solve.py has banked it — profile status and sweep-point count written to results/state/solved.txt. Teardown of a banked workspace releases with close_projects=False; teardown of an unbanked workspace that shows solve evidence refuses, because releasing it would purge the solved results. That incident happened once, on a pilot, and this is the structural answer to it.

Readout and Result QA

Result QA checks the signals agreed in Clarification — convergence, ports excited, energy pass, in-band resonance, plausibility against the recipe — flags anomalies, and reports them. Only the user decides whether results are junk. After any anomaly the rule is resolve once: read the profile, escalate with the evidence, never re-submit silently (a pilot submitted five solves for a one-solve problem).

Retrieval is treated as its own fragile seam. read_results.py is the single home for the call shapes that actually work on pyAEDT 1.3.0 — the ubiquitous data_real fill-state check does not exist on this version, so it reported "unfilled" on perfectly good fetches and discarded them. Scripted readout is capped at one attempt plus one retry on a fresh attach; then the plot goes to the user and the signal is reported as read from the UI. The delivery route is recorded per run.

§ 08Gates and refusals

Nine hard rules, each traceable to a decision record or a measured failure. The ones that matter most are the ones that refuse rather than advise.

  1. 1
    High-level API only. Every call goes through ansys.aedt.core; the raw COM surface is broken over gRPC. Unknown calls are looked up, never guessed. env-compat #3
  2. 2
    The Review gate is visual. The user reviews the model in the AEDT UI, never the scripts. Nothing solves until they pass it. ADR 0003
  3. 3
    Read-back sync after every tweak. No gate closes until sync has run and the record reproduces the delivered model. ADR 0005
  4. 4
    Playbook discipline. Technique is appended only through the Learning loop's ceremony, after explicit user approval. Nothing appends silently. ADR 0002
  5. 5
    Re-entry copies. The original project is never opened; work happens on a copy. ADR 0001
  6. 6
    Full parameterization. All geometry is built from design variables, so a user tweak is a variable edit — readable, syncable, re-solvable.
  7. 7
    Idempotent stages. Delete-then-create; wipe-and-rebuild is an escalation, not a route-around. ADR 0008
  8. 8
    Never build the missing capability. If a recipe needs synthesis or a solver this repo does not implement, stop and escalate with what is missing and what it would take. A Clarification block locks parameters; it never becomes an implementation project.
  9. 9
    Solve under the watchdog, bank before teardown. Read machine state only; evidence before claiming; nothing closes the desktop before solved.txt exists. ADR 0006

Why some of these are code and not prose

A campaign of parallel test cells measured the honest answer. Six specs passed validate_spec, precheck and compile_spec --dry-run with zero errors and zero escape hatches — and three of them were wrong: a false-green rate of 50%. No automated gate could see any of the three. Two were caught by a human reading the spec; one only because the reviewer knew the design convention.

The two cheapest of those holes are now closed by computation rather than advice — the λ₀/3 clearance rule and the port-geometry ratio in §05 — and the third, a feed network whose elements were mismatched to the impedance they terminate into, is recorded as an open gap rather than papered over. The session boundary and the call budget come from the same campaign: a documented limit that gets read, quoted and ignored is not a limit.

Fixture fidelity

Tier 0's ground truth is captured off this machine, never written from memory, and that rule is itself enforced: a corpus presence check fails loudly rather than letting the real-artifact tests turn quietly into no-ops. It exists because two production bugs passed 72 green tests — a profile fixture written with unescaped quotes where AEDT writes escaped ones, and artifact families written as files where the real tree has directories. A synthetic fixture is valid only alongside a real one it provably matches.

The playbook

Environment compat

knowledge/playbook/environment-compat.md

The compat authority for this machine: 13 probed findings with verdicts and route-arounds — what works, what is partially broken, what is present but unusable. Standing prerequisites (VPN reachability for the licence server, AEDT 2024 R1 launchable) are preconditions the tool blocks on rather than works around.

Canonical cases

knowledge/cases/

Five worked cases — patch 2.4 GHz, bow-tie 3.5 GHz, 50 Ω microstrip, 10 GHz pyramidal horn, coupled-line filter 2.4 GHz — four with a compiled design.yaml to start from, plus five captured snapshots of real models used to shape the schema.

The fifth is deliberately spec-less: coupled-line even/odd-mode synthesis is not implemented here, and that gap is the standing example behind hard rule 8.

Reference papers

knowledge/reference-papers/

The user drops PDFs — papers, book chapters, port and HFSS primers — and an analysis skill turns them into notes read before Clarification. They are context: only an approved Learning-loop proposal can turn a paper into playbook technique.

The Learning loop

ADR 0002

Three triggers earn an amendment proposal: a user tweak that generalizes to the recipe class, a backend-compat discovery, or a QA anomaly whose resolution generalizes. The order is fixed — fix the current model first, then propose, and append only after approval. Project-specific values stay in the summary.

§ 11Measurement

The tool measures itself, and the metric is cost per completed simulation. A run that burns tokens and delivers no readable result scores as infinite, not as somewhat worse.

scripts/run_card.py reads the session database read-only and emits the run card appended to every summary.md: billed tokens, step count, raw wall time, and active wall — Clarification start to the user-gated solve submission, so solver physics and idle gaps do not flatter the number. A missing boundary is reported as unmeasurable, never guessed.

§ 12What is not proven

Stated plainly, because a capability report that only lists capabilities is a sales document.

No language model has ever authored a design.yaml

Every spec in the repo was hand-written or reduced from a snapshot. The compiler is proven on hardware; the authoring step in front of it is not, and it is where the remaining risk concentrates. Relatedly, no full run has yet gone through Route A end to end — the compiler has never been driven by an agent in a real pilot.

The false-green rate is 50%, measured

Three of six machine-clean specs were wrong. Two of those three holes are now closed by computed checks; the third — a feed network mismatched to the impedance it terminates into — is not implemented. A spec passing every gate means the mechanical properties hold, not that the design is right. The human gates are load-bearing, not ceremonial.

The phase boundary has one known hole

It covers every expensive action that goes through this repo's own tooling — launching a desktop, compiling onto one, solving. It cannot stop an arbitrary python -c in a shell call, which is exactly how the measured 51-minute field-solver detour was written. Closing that needs per-phase tool gating in the harness, and it is recorded as open work rather than claimed.

Not implemented, by decision

Coupled-line even/odd-mode synthesis (hard rule 8's standing example). Explicit mesh operations in schema v1 — adaptive-only. Geometry received rather than designed, which takes import_cad and accepts that imported bodies carry no construction history and cannot be parameterized. RCS/SBR+ is present in the client but not usable on this backend, so an RCS pivot routes around it.

The next structural piece

A deterministic orchestrator: a Python state machine that walks the Spine and calls a model at exactly three seams — clarify (request → spec draft plus questions), diagnose (failure evidence → spec patch or escalation), and narrate (QA signals → summary prose), each with structured output against the schema so a malformed response is a decoding retry rather than a failed AEDT run. The session boundary and the call budget are its first two pieces and are landed; the rest is not.
