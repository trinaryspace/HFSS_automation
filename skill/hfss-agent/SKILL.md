# HFSS Agent

Turn one conversation into three named phase sessions that together deliver a complete, correct HFSS simulation on the live AEDT desktop: geometry, materials, excitations, setups, a solved result, and the requested plots — driven by idempotent staged scripts through the Spine, with the user reviewing the Math model in the UI before any solve.

The `.rst.md` files under the KB are stubs — **never read or grep them**; for filename discovery use `rg -l`, never full recursive listings.
5. `scraping/pyaedt_ai_context/` — the full KB for any call not distilled in `spine-api.md`; the read-only `kb-lookup` subagent answers exact-signature questions from it.

## Preconditions — block and escalate if unmet

- UM VPN connected: the license server must be reachable (env-compat “Standing prerequisites”); verify reachability before any run that opens a design or solves.
- AEDT 2024 R1 (`v241`) running or launchable; pyAEDT 1.3.0 via `ansys.aedt.core` (the `pyaedt` alias does not exist — env-compat).
- If a precondition fails, stop and report the evidence; do not work around it.

## Hard rules (ADR-backed)

1. **High-level API only.** Every call goes through `ansys.aedt.core`; never the raw COM surface (SetActiveDesign, GetDesignNames, GetActiveProjectName, GetMessages… are broken over gRPC — env-compat #3). Before promising any API, check the environment-compat entry; route around what it marks unsupported (e.g. RCS/SBR+ — env-compat #12). Unknown calls are looked up via `kb-lookup` or `spine-api.md`, never guessed.
2. **Visual Review gate.** The user reviews the built Math model in the AEDT UI — never to the scripts (ADR 0003). Nothing solves until the user passes the gate.
3. **Read-back sync.** After every user UI tweak, introspect the live model — the sync amends the owning stage's script so re-running top-to-bottom reproduces the delivered model; record the delta in the summary; no gate closes until sync has run (ADR 0005).
4. **Playbook discipline.** The playbook grows only through the Learning loop's amendment ceremony with explicit user approval (ADR 0002). Nothing appends silently.
5. **Re-entry copies.** Re-entry never opens the original Project: copy it (results included) into the Workspace first, work on the copy only (ADR 0001).
6. **Full parameterization.** All geometry is built with design variables; user tweaks are variable edits — readable, syncable, re-solvable.
7. **Idempotent stages.** Every staged script deletes the objects, boundaries, excitations, mesh operations, and sweeps it (re)creates before creating them, so re-running any stage in place converges (ADR 0008). Wipe-and-rebuild is demoted to an explicit escalation tool — never the default route-around.
8. **Never build the missing capability.** If the Recipe needs synthesis, a solver, or a method this repo does not implement — coupled-line even/odd-mode synthesis is the standing example — **stop and escalate to the user with what is missing and what it would take**. Do not implement it, not as a helper, not "just to get the numbers", not inline in a bash call. Report the gap and let the user decide: pick a different structure, supply the dimensions, or approve building the capability as its own piece of work. *Measured 2026-08-17 (cell S11): asked for a coupled-line filter, the agent found the gap, quoted the playbook note that says the synthesis is not implemented, and then spent 51 minutes and 151,526 tokens writing and debugging a 2D finite-difference field solver inside a Clarification block. It delivered nothing. The knowledge was present, correct and read; it did not bind, because it was written as a note rather than as a rule. This is the same shape as the 25-hour `shiny-canyon` pilot.* A Clarification block locks parameters; it never becomes an implementation project.
9. **Solve under the watchdog, and bank before teardown.** The solve is submitted by `08_solve` and watched by a detached, stage-aware `poll_solve` writing machine state; you read machine state only — the solve's own state is `solve_progress.txt`, tailed not read whole — never foreground-poll, never estimate solve time, never pass a predicted output count (ADR 0006, amended). Terminal states are evidenced by the profile's `Status` line, never inferred from a plateau. A solve is not finished until `confirm_solve` has **banked** it to `results/state/solved.txt`; teardown refuses an unbanked workspace that shows solve evidence, and a banked one releases with `close_projects=False`. After any anomaly: read the profile once, then escalate — never re-submit silently.

## The run — three phase sessions bound by the State ledger

One run is **three named phase sessions** (ADR 0007), each starting fresh from `workspaces/<name>/state.md` — the **State ledger** — not from the prior conversation. **Declare the phase as the session's first action** — `python scripts/session.py --workspace workspaces/<name> --phase <clarify|build|solve>` — which turns on the boundary: once declared, the repo's entry points refuse out-of-phase work (a clarify session cannot launch a desktop; only a solve session may solve), and the session carries a call budget that escalates rather than looping. An undeclared session is unguarded, so this is not optional ceremony: it is what makes hard rule 8 and the session budget enforceable instead of advisory. Each session amends the ledger as it goes and leaves machine state in `results/state/*.txt`. Resume points are only the ledger: a killed session resumes from it instead of redoing Clarification or script-writing. The sessions are named `<name>-clarify`, `<name>-build`, `<name>-solve`.

- **Session 1 — Clarification** (`<name>-clarify`) — one block, nothing builds before it. Gather the minimum information, spot critical setup features the user left out, map the request onto a playbook Recipe (or derive a new one), state every Assumption explicitly, propose the Result QA signals, and lock the parameters/variables. *Done when: the user confirmed the Recipe, the assumptions, and the QA signals* — and the State ledger is written (`state.md`: locked parameters/variables, Recipe, QA signals, pending decisions).
  - **Paper-sourced Recipes — dimension gate before anything builds.** When the Recipe comes from an academic paper, the Clarification block first numerically cross-checks the paper's equations against its own Table and Figure readings (from the analyze-papers notes) for the key dimensions — base / height / feed — and prints one verdict line: `dims cross-check: consistent`, or with the actual disagreeing numbers when readings clash, e.g. `dims cross-check: INCONSISTENT — ⚠ Table says 46×23, Figure says 52.64×26.32`. An inconsistent paper is not a buildable Recipe: the block asks the user to arbitrate which reading is canonical (Table / Figure / equations) or to reject the paper; nothing builds until the dims are locked, and the State ledger records the canonical source per key dimension. **Run the closed-form pre-check on the locked dimensions** — `python scripts/precheck.py <spec>` predicts the design's target from textbook relations and prints the signed disagreement; an `INCONSISTENT` verdict goes to the user with both numbers, and it never blocks and never overrides them. The block also locks the results path up front: S11 will be read via the AEDT UI on this box; a scripted readout is a bonus, never a blocker — no run stalls on retrieval discovery later. Recipes not sourced from a paper keep the Clarification exactly as before.
- **Session 2 — Build** (`<name>-build`) — walk the Spine stages below on the live AEDT desktop by one of the two **Build routes**; each stage ends with its Verification line and a one-line ledger delta. Close with the Review gate and read-back sync. *Done when: validation passes, the user passed the gate, read-back sync printed its PASS line, and the ledger records the snapshot pointer.*
- **Session 3 — Solve + QA** (`<name>-solve`) — read the ledger; submit the solve under the detached watchdog; read only machine state while it runs; make the Recipe plots; run Result QA; deliver `summary.md` with the run card appended by the measurement harness. *Done when: the requested plots exist in `results/`, every agreed QA signal is reported, and `summary.md` holds the run card.*

### Build routes — Design Spec first, staged scripts as the fallback

The Spine below is the same either way. What differs is who writes the code that walks it.

- **Route A — Design Spec (preferred).** Write **one** `workspaces/<name>/design.yaml` and let the tested compiler build it. Gate it offline first — `validate_spec.py`, then `precheck.py`, then **`preview_spec.py`**, all three no-license and about a second — then `compile_spec.py --dry-run`, then `--launch`. The compiler is idempotent by construction, resolves symbolic face selectors itself, emits the same `PASS:` Verification lines, and has absorbed the pyAEDT defects earlier runs paid for. Proven on this box: it rebuilt the pilot's bow-tie with **zero snapshot differences and zero bbox differences**, and built the microstrip and the horn clean first try. Full route: `reference/design-spec.md`.
- **Route B — staged scripts.** One stage = one `NN_<stage>.py`, as below. Use it when the schema cannot express the structure, and **say so in the ledger** — per-stage escape hatches are a tracked metric, not a quiet convenience.

**Choose Route A unless the structure defeats the schema.** Four canonical cases already have specs to start from (`knowledge/cases/*/design.yaml`), and `patch-2400` describes a model that has been built and solved here.

### The Spine, in the Build session

Under Route A the compiler walks these stages for you; under Route B you write one script each. One Stage = one staged script (`NN_<stage>.py` in Workspace `src/`) = one Run. A stage is done when its completion criterion below is met **and** the user has seen the stage's state in the open desktop. Walk in order; a failed completion criterion makes the stage a failed Run (self-correction, below).

1. **Solution type** — set from the Recipe, explicitly (never the default — env-compat #11). *Done when: the design reports the Recipe's type.*
2. **Design** — create the design in the Workspace Project and save (`remove_lock=True` if a stray lock exists — env-compat #9). *Done when: the project file exists on disk with the named design.*
3. **Geometry** — every dimension a design variable; units per recipe; delete-then-create each solid so re-runs never duplicate (ADR 0008). *Done when: the Model's solids match the Recipe in the UI and each dimension is a variable, not a literal.*
4. **Materials** — per Recipe; tunables as variables. *Done when: each solid reports its Recipe material.*
5. **Excitations / boundaries** — port strategy per Recipe; port assignment by **face object** on a solid's face — never ids/edges, and beware sheet-port auto-integration (env-compat #7/#8). *Done when: the ports/boundaries list matches the Recipe.*
6. **Mesh** — Recipe mesh operations, or adaptive-only for proof stages. *Done when: the mesh operations list matches the Recipe (or is deliberately empty).*
7. **Setup + sweep** — per Recipe (adaptive passes, delta-S, frequency, sweep range/interp). *Done when: `existing_analysis_sweeps` shows the named setup with its sweep.*
8. **Validation** — `validate_simple()` must pass; an invalid design is a failed stage (env-compat #8). Because every script is delete-then-create, a re-run in place always converges (ADR 0008). *Done when: validation returns True.*
9. **Review gate** — present the fully built Math model in the AEDT UI; the user inspects and may tweak; run read-back sync and verify it deterministically: `capture_state.py` writes `model_snapshot.json`, then `12_verify_sync.py` replays the amended staged scripts on a fresh copy on a port-pinned second desktop, diffs, and prints one PASS/FAIL line. *Nothing solves until the user passes the gate.* *Done when: the user passed the gate, sync verify printed PASS, and the ledger holds the snapshot pointer.*

### Solve + QA, in the Solve+QA session

- **Solve under the stage-aware detached watchdog** (ADR 0006, amended) — `08_solve` cleans stale results (skip-if-no-stale: `cleanup_solution` raises `GrpcApiError DeleteFullVariation` on a first-ever solve), probes for a solve already in-flight (results-dir age + live solver processes) and **asks the user before submitting if one looks live**, submits `analyze(setup=…, blocking=False)` — its `True` return means *submission*, not completion (env-compat #5) — and launches the detached `poll_solve` watchdog via `subprocess.Popen(DETACHED_PROCESS)`. The watchdog appends one line per ~20 s to `results/state/solve_progress.txt` carrying its **stage** (initial meshing / adaptive meshing / frequency sweep / finalizing / done) plus the evidence for it, and exits **0 complete / 2 stalled / 3 aborted**. Terminal states are evidenced, never guessed: completion requires the profile's `Status: Normal Completion`, and **no output-count prediction is ever passed** — there is no `EXPECTED_SD`. While it runs: **tail `solve_progress.txt` only — never read the whole file, never foreground-poll, never estimate**; re-attach (fresh session) for model reads if needed (env-compat #6). *Done when: the watchdog's terminal line names complete with the profile status.*
- **Resolve-once** — after any solve anomaly, read the profile once and **escalate to the user with the evidence**; never re-submit without the user knowing. (The pilot submitted five solves for a one-solve problem.)
- **Bank before teardown** (ADR 0006 amendment) — the solve session is not over until the evidence is persisted: run `python src/confirm_solve.py` to write `results/state/solved.txt` (profile status + sweep-point count). Teardown of a banked workspace uses `close_projects=False`; `ws_common.teardown()` **refuses** an unbanked workspace that shows solve evidence, because releasing it would purge the solved results. *Done when: `solved.txt` exists.* **Nothing closes the desktop before this.**
- **Post-process + reports/plots** — Recipe plots, delivered to `results/`. *Done when: each requested plot exists in `results/`.*
- **Result QA** — check the agreed signals: convergence, ports excited, energy pass, in-band resonance, plausibility against the Recipe. Flag anomalies and report them; only the user decides whether results are junk. **Readout is one shot**: at most one scripted `get_solution_data` attempt plus one retry on a fresh attach, then hand the plot to the user and report the signal as read from the UI — never iterate readout shapes (the pilot tried eight and ended the run). Record which route was used. *Done when: every agreed signal is reported (or explicitly "unreadable — flaky readout, UI-arbitrated") and anomalies are surfaced.*
- **Summary + run card** — the acute design decisions + what the Model is; have the `runcard` subagent draft the summary sections and the `## Run card` from `state.md`, `results/state/*.txt` and `results/`, revise the draft, then append the Run card via the measurement harness (`scripts/run_card.py --summary …`). Deliverables: the project file, the requested plots, and `summary.md`. *Done when: `summary.md` is written per the template and the run card is appended.*

**Re-entry** runs the same ceremony on the copy: introspect the copy and report a model card (designs, solution types, setups, boundaries, materials, variables, existing results) first. A pivot (e.g. antenna → RCS) is a recipe switch — handled as a fresh Clarification.

## Execution mechanics

- **Staged scripts**: one file per stage `NN_<stage>.py` in the Workspace `src/`, carrying the attach-or-launch preamble and following the per-stage checklist — both in `reference/execution.md`. **Verification contract**: every staged script ends with one machine-parseable Verification line, `PASS: <stage> <assertions>`; a static gate — `py_compile` + import check over all `src/*.py` — runs before any AEDT launch. Session state lives in the AEDT project, never in a Python process.
- **Runs and self-correction**: after every Run, read the Verification line — not filtered logs — plus the other working error surfaces (`validate_simple()`, on-disk logs; `GetMessages` is broken over gRPC, env-compat #3). Cap self-correction at 3 consecutive failed Runs per Stage; escalate on the cap, on the identical error twice in a row, or on an error unmapped to any KB/playbook cause — with the script, the error, and the attempted fixes attached. Because stages are idempotent, a re-run is one in-place script Run — no teardown → wipe → replay chains. Full detail: `reference/execution.md`.
- **Look at the geometry before AEDT does, and before the user does.** `python scripts/preview_spec.py <spec>` renders three orthographic views to a PNG in about a second with no license and no desktop — then **read the PNG back and inspect it**. Every defect the Review gate has caught in this project has been *relational* (an element built unlike its copies, a port normal to the wrong axis, metal that does not touch, a boundary flush against the model), and relational defects are visible in a drawing while being invisible to field-wise validation. Run it after writing the spec and after every geometry edit; the AEDT Review gate then confirms a model you have already looked at instead of discovering it. It draws axis-aligned bounds only, and names under "not drawn" anything it could not resolve — those junctions still need the UI. *Measured 2026-08-18: four Review-gate defects, four diagnose-fix-rebuild cycles, each paying a full launch and compile; three of the four are visible in this drawing.*
- **Session budget — stop and ask rather than push on.** A Clarification block that has not locked its parameters, or a Build session that has not produced its artefact, after roughly **60 tool calls** is not close to finishing; it is looping. Stop at that point, report what is done, what is blocking, and what the remaining options are, and let the user choose. *Measured 2026-08-17: cell S11 spent 250 parts and 151,526 tokens across 51 minutes and delivered nothing, having decided at around call 20 to write a field solver (hard rule 8). The cost was not the wrong decision; it was the 200 calls after it with nobody to notice.* This bound applies per session and is a floor for escalation, never a licence to spend up to it.
- **Bash discipline**: pass an explicit `timeout` to any bash call that can exceed ~90 s; never take full recursive directory listings — use count/size summaries, `tail`, and `results/state/*.txt`; keep final agent messages ≤ ~250 words.
- **Release hygiene**: keep the desktop alive across stages (the next staged script's preamble attaches to it); at session end close the session and reap the launched server process (kill-until-gone — env-compat #10) — but **never before the solve is banked** (`results/state/solved.txt`), because releasing a solved-but-unbanked workspace purges its results. Verify-runner teardown is **port-pinned**: only the runner's own desktop is killed — the user's desktop is never touched. `os._exit` after teardown because gRPC teardown hangs otherwise. Full preamble: `reference/execution.md`.
- **Learning loop**: when a user tweak generalizes to the Recipe class, or a backend-compat discovery surfaces, or a QA anomaly's resolution generalizes — fix the current Model first, THEN propose the playbook amendment, and append only after approval. Project-specific values stay in `summary.md`. Triggers and ceremony: `reference/execution.md`.

## Workspace shape and deliverables

Every conversation gets a Workspace: `state.md` (the State ledger), `src/` (staged scripts), the project file, `results/` (deliverables + `state/*.txt` machine state), `summary.md` (incl. the `## Run card` and the snapshot pointer). The template lives in `templates/workspace/` (README + summary skeleton). Tool and knowledge directories stay clean; workspace outputs are gitignored.
